# Reproducible offline evaluation

## Run the supplied experiment

Build and run the automated tests before evaluating:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
python3 scripts/run_eval.py --out artifacts/evaluations/real-smoke-001
```

The runner defaults to `data/evaluation/real_smoke/dataset.json`, `build/tabletop_recognition_eval`, `build/tabletop_recognition_train`, and `configs/eval.yaml`. It never opens a camera. An explicit output directory must not already exist; omit `--out` to create a unique timestamped directory.

Useful options:

```sh
python3 scripts/run_eval.py --validate-only
python3 scripts/run_eval.py --dataset /path/to/dataset.json --out artifacts/evaluations/another-run
python3 scripts/run_eval.py --binary /path/to/tabletop_recognition_eval --train-binary /path/to/tabletop_recognition_train --out artifacts/evaluations/another-build
```

A successful exit means the experiment completed without processing errors. It does not require every prediction to be correct. Read `report.md`, `summary.json`, and the individual result rows before interpreting the result. A run with missing images, decoding failures, pipeline errors, or failed failure-image writes returns nonzero; evidence already written is retained for investigation. Dataset validation can fail before a run directory exists; for example, the runner rejects a missing source file during preflight.

## What the current smoke dataset establishes

The supplied pack contains five real single-object images whose labels were confirmed by the owner (`annotation_status: owner_verified`). Training uses a fixed, hashed copy of `data/object_db.csv`: five rows in the original `label,f0,f1,f2,f3` format.

Those four values use the main pipeline's `shape4d` representation: fill ratio, aspect ratio, and signed-log first and second Hu moments. They are imported directly into a new SQLite database; the logarithmic transform is not applied a second time. The field layout is compatible, but the vectors were generated by the legacy pipeline and have not been re-extracted by the refactored pipeline. This is a nearest-neighbor reference set, not neural-network training.

The old feature rows have no traceable source-image or capture-session records. Independence between that training set and the five evaluation images cannot be established. An owner-confirmed class label establishes the annotation, not train/test independence. Any accuracy from this pack describes these fixed inputs only and must not be represented as generalization performance.

## Dataset descriptor and sample metadata

The Python runner consumes a dataset descriptor and a metadata CSV. These are separate from the smaller manifest accepted by the C++ evaluator.

The descriptor uses schema version `1`, a name containing letters/digits/underscores/hyphens, `purpose` (`smoke` or `holdout`), `annotation_status: owner_verified`, `manifest`, and `training`. Paths in the descriptor are relative to its directory. The metadata CSV must have exactly this header:

```csv
sample_id,image,label,split,group_id,sha256
```

| Field | Meaning |
|---|---|
| `sample_id` | Unique stable identifier using letters, digits, underscores, and hyphens |
| `image` | Image path relative to the metadata CSV, or an absolute path |
| `label` | Owner-confirmed ground truth |
| `split` | `train` or `test` |
| `group_id` | Capture group used to keep related images in the same split |
| `sha256` | Expected SHA-256 of the image bytes |

Validation rejects missing files, changed hashes, duplicate IDs, duplicate paths, duplicate image content, invalid labels, and datasets without test images. It also checks the training mode:

- `training.kind: legacy_features` requires a feature CSV `path` and its `sha256`. It is allowed only for `purpose: smoke`, with no image rows marked `train`.
- `training.kind: images` requires train images. Training and test `group_id` sets must be disjoint. `Unknown` is reserved for unseen test objects and cannot be a training label.
- `purpose: holdout` additionally requires a documented `collection_protocol` and capture groups other than `unknown` or `unverified`.

Capture groups must describe the actual collection process. Grouping adjacent frames from one recording separately does not make them independent. For future holdout data, record the recording/session and physical object identities, keep related observations together, and freeze the test set before tuning thresholds. The validator can check the declared IDs and hashes; it cannot verify that the declared collection history is true.

The labels `NoDetection`, `MissingImage`, `UnreadableImage`, and `PipelineError` are reserved for evaluation outcomes.

## Prepare a hashed sample manifest

Start with reviewed annotations whose header is exactly:

```csv
sample_id,image,label,split,group_id
```

Then fingerprint the listed images:

```sh
python3 scripts/prepare_dataset.py /path/to/reviewed_annotations.csv \
  --output data/evaluation/new_set/samples.csv
```

Input image paths resolve relative to the annotation CSV. The generated six-column metadata CSV adds `sha256` and rewrites image paths relative to its own directory. The helper preserves explicit labels; it never derives classes from filenames or folders. It rejects missing files, duplicate image content, invalid splits, and capture groups shared by training and test rows, and refuses to overwrite an existing output.

Create the dataset descriptor separately, document the training source and collection protocol, and record `owner_verified` only after the owner has actually confirmed the labels. Preparing hashes neither creates that descriptor nor assigns annotation-review status.

## Native evaluator contract

The C++ evaluator accepts exactly two CSV columns:

```csv
image,label
images/first.jpg,camera
images/second.jpg,Unknown
```

Pass the file using `--manifest`, or set `evaluation.manifest_path` in the configuration. An absent, empty, or malformed manifest fails before starting a run. Double-quoted CSV fields and escaped quotes are supported, but fields must fit on a single physical line. Duplicate normalized paths, including symlink aliases, are rejected.

Relative image paths resolve against the manifest's directory. An explicit `--dataset <directory>` overrides that root. There is no basename lookup, filename-based label inference, directory scan, or image-glob filtering. Only listed images are evaluated, in manifest order. The original `input.image_dir` value does not override the manifest root.

For an already populated training database, the lower-level command is:

```sh
./build/tabletop_recognition_eval --config configs/eval.yaml \
  --manifest /path/to/manifest.csv \
  --database /path/to/trained.sqlite3 \
  --artifacts artifacts/manual-eval-001 \
  --out artifacts/manual-eval-001/results
```

The native command reads and adds run records to the selected database. Use the Python runner when you want automatic isolation and a frozen training/input snapshot.

Each result row identifies the resolved image path and contains `true_label`, `predicted_label`, `score`, `latency_ms`, `correct`, `status`, and `detection_count`:

| Status | Interpretation |
|---|---|
| `ok` | A region was detected and its predicted label matches the truth |
| `misclassified` | A region was detected but its predicted label differs |
| `no_detection` | No region survived filtering; prediction is `NoDetection` |
| `missing_image` | A listed image is absent; prediction is `MissingImage` |
| `unreadable_image` | A listed path cannot be decoded as an image; prediction is `UnreadableImage` |
| `pipeline_error` | Processing raised an exception; prediction is `PipelineError` |

`Unknown` is a normal classifier rejection on a detected region. A blank image labeled `Unknown` still fails when no object is detected. Missing/unreadable/exception rows remain in the result set and accuracy denominator; they are never silently skipped. The runner validates that the native output contains exactly one row per test image and that its truth labels match the frozen manifest.

This evaluator scores one label per image using the largest retained region. `detection_count` counts retained candidates after area, boundary, and maximum-region filtering; it is not a count of all objects visible in the image. Neither these results nor their confusion matrix constitute a multi-object detection or tracking benchmark.

## Metrics and timing

`summary.json` reports total/correct counts, accuracy, per-status counts, per-class support/precision/recall, and pipeline mean/P50/P95 latency. Accuracy includes all listed test inputs. Per-class precision is zero when the classifier never predicts that class.

For `ok`, `misclassified`, and `no_detection`, `latency_ms` is the pipeline's measured total, including rendering. It excludes image decoding, per-frame logging, and failure-image writes. No warmup is performed. Missing/unreadable/pipeline-error rows record the elapsed failed stage and are excluded from the pipeline latency distribution. P50/P95 use linear interpolation over the sorted completed-pipeline measurements.

The native `results/metrics.json` also contains average stage timings and `avg_fps`. That rate divides attempted entries by the evaluation loop's elapsed wall time, which includes image reads and per-image artifact work; it excludes setup and final exports. It is not live-camera FPS. Native average pipeline latency and stage timings divide by `completed_pipeline_frames`; failed-stage latency is reported separately as `avg_failed_stage_ms`. Failed inputs do not artificially lower the average pipeline latency.

Five inputs provide little evidence about a latency distribution, and measurements depend on the machine, build, inputs, and startup effects. Synthetic CTest performance fixtures are regression checks, not substitutes for a representative real-image/video benchmark.

## Export a summary from existing predictions

To recompute metrics from a native result CSV:

```sh
python3 scripts/export_metrics.py /path/to/results/eval_results.csv \
  --purpose smoke --output /path/to/summary.json
```

The input must contain all eight native fields: `frame_id,true_label,predicted_label,score,latency_ms,correct,status,detection_count`. The exporter uses the same summary implementation as the experiment runner and validates that statuses, detection counts, truth/prediction labels, and `correct` agree. Older CSVs without status and detection count are rejected. Failure rows remain in the accuracy denominator and failed-stage timings are excluded from pipeline percentiles.

Omit `--output` to print JSON. `--purpose` defaults to `smoke`; passing `holdout` only declares the intended purpose and does not validate a dataset, reconstruct its split, or prove independence.

## Preserved outputs

```text
<output>/
  report.md                         Human-readable results and limitations
  summary.json                      Accuracy, statuses, class metrics, latency summary
  provenance.json                   Source/binary/config hashes, environment, commands
  dataset_original.json             Unchanged original dataset descriptor
  dataset_source.json               Replay descriptor with paths rebased to this output
  config_source.yaml                Original configuration file copy
  samples.csv                       Frozen sample IDs, splits, groups, hashes
  inputs/                           Frozen image copies
  training_features.csv             Frozen legacy features, when applicable
  eval_manifest.csv                 Exact native image,label manifest
  vision.sqlite3                    Isolated training samples, run, and predictions
  eval.log                          Native evaluator stdout/stderr
  results/
    eval_results.csv                One result row per test image
    confusion_matrix.csv            Outcomes including detection/processing failures
    metrics.json                    Native metrics
  artifacts/
    runs/<run>/
      config_snapshot.yaml          Resolved runtime configuration and command
      eval_manifest.csv             Resolved native manifest snapshot
      run.log                       Per-frame events and timings
      metrics.json                  Native metrics copy
    failures/                       Failed-image overlays when an image is available
```

Image-based training also creates `training_artifacts/`, `training_crops/`, and per-sample training logs. Missing/unreadable files cannot yield an overlay; their status and exception remain in the CSV and log.

Hashes identify the inputs and executable used. They do not by themselves prove that a binary was built from the recorded source, so build and test immediately before the run and retain that build evidence. If Git has no commit, provenance records that limitation rather than inventing a revision.

## Replay frozen inputs

`dataset_original.json` preserves the original descriptor. `dataset_source.json` is the replay descriptor: its manifest points to the frozen `samples.csv`, and legacy training points to the frozen `training_features.csv`. Sample image paths in `samples.csv` are relative to the experiment directory. This keeps replay independent of the original files even when the original manifest or feature source used a nested or external path.

Replay into a new directory using the stored configuration:

```sh
python3 scripts/run_eval.py \
  --dataset /path/to/previous-run/dataset_source.json \
  --config /path/to/previous-run/config_source.yaml \
  --out /path/to/replayed-run
```

The runner creates another isolated database and regenerates runtime paths. Integration tests cover replay after deleting the original image files and replay of legacy features originally stored under a nested path. Previously recorded native commands and configuration snapshots still contain their original absolute paths; use the replay descriptor through the runner instead of executing stale commands after moving an experiment directory.

Replay uses the currently selected binaries and environment. Pass `--binary` and `--train-binary` when selecting a particular build, and compare recorded fingerprints before attributing changes in predictions or timing to the software.
